# M8 第 6–7 项提案：隔离插件运行时

> 状态：**待用户批准**，未实施。
> 依据：`AGENT.md` §8.5「插件安全」、§13.2「第三方插件属于扩大执行权限，必须先说明并获得确认」、
> §13.3 提案格式要求。第 6 项（隔离进程）与第 7 项（安装/禁用/卸载/版本）耦合很紧，
> 一起提案，但**分批实施**。

---

## 1. 背景与当前问题

MCP 接入（D-016）已经能运行**外部进程**，但它有两个关键前提：
一是 Server 由用户自己挑选并显式配置，二是连接只是"通信"，我们不管理它的生命周期。

M8 第 6–7 项要求的是另一件事：**安装、启用、调用、停止、卸载第三方插件**。
插件是别人写的代码，要在本机执行。这是整个项目里权限最敏感的一步——
比 MCP 更敏感，因为 MCP Server 至少是用户手动指定的，而插件要经历
"发现 → 安装 → 运行"的流程。

`AGENT.md` §8.5 的硬性要求逐条列出，本提案逐条回应：

| §8.5 要求 | 本提案如何满足 |
|---|---|
| 第三方插件默认隔离运行 | bubblewrap 沙箱，独立 mount/pid/net/user 命名空间 |
| MVP 不执行第三方任意代码 | **本期仍不执行任意代码**，见 §2 非目标 |
| 使用低权限用户/受限容器或合适沙箱 | bwrap + 降权 + 只读根文件系统 |
| 为 CPU、内存、时间、文件、网络和子进程设置限制 | RLIMIT + 超时 + 无网络命名空间 |
| 宿主通过受控 Broker 暴露资源 | 插件只能经 JSON-RPC 调用宿主的受限 API |
| 插件不能直接访问主数据库文件和 Keychain | 沙箱内看不到数据库文件；环境变量不含密钥 |
| 安装前显示来源、权限、依赖和风险 | 安装预览界面 + 显式确认 |

## 2. 目标与非目标

### 目标

- **插件是"声明式能力包"**：一个目录，含 `plugin.json` 清单与可选的
  可执行入口；
- 能**安装**（从本地目录/压缩包）、**列出**、**启用/禁用**、**卸载**；
- 插件声明的工具经 Broker 调用，与内建工具、MCP 工具走**同一条** Policy/审批链路；
- 插件进程**在沙箱中运行**：无网络、只读根文件系统、CPU/内存/时间受限；
- **停止**一个卡住或行为异常的插件进程；
- 生命周期事件可追溯（谁装了什么、什么时候启用）。

### 非目标（本期不做）

- **不执行插件里的任意 Python/JS 代码**。本期的"插件"只有两个来源：
  1. 声明式插件：只声明**复用已有的内建工具与技能**（组合，不含代码）；
  2. 进程插件：用户自己提供的可执行文件，在沙箱里运行——但**默认禁用**，
     且需要用户在安装时对"将执行可执行文件"做出显式确认。
- WASM（第 8 项）
- 社区市场、签名验证、自动更新（M10）
- 插件的 UI 扩展

**为什么第 1 类插件先做**：它能立刻满足 M8 验收里"被发现、授权、调用、
停止和卸载"的全部动词，而风险接近于零（没有任何第三方代码被执行）。
第 2 类在同一套运行时上追加，但需要用户明确启用。

## 3. 备选方案

### 方案 A：bubblewrap（本机实测可用）+ RLIMIT

```
bwrap --unshare-all --unshare-net --die-with-parent --new-session \
      --ro-bind /usr /usr --symlink usr/lib /lib ... \
      --ro-bind <plugin-dir> /plugin \
      --tmpfs /tmp --proc /proc --dev /dev \
      prlimit --as=<mem> --nproc=<n> --cpu=<s> -- <entrypoint>
```

**本机实测结果**（不是推测）：

- `bubblewrap 0.9.0` 已安装，功能性测试通过；
- `--unshare-net` 后 `socket.create_connection(('1.1.1.1', 443))` 抛 `OSError`，
  **出站网络确实被阻断**；
- `prlimit` 2.39.3 可用，`--as` / `--nproc` 生效；
- `unprivileged_userns_clone=1`，无需 root。

**优点**：轻量、无需 daemon、启动快、真隔离。
**缺点**：Linux 专属；macOS/Windows 需要各自的方案（留到桌面阶段）；
bwrap 本身是外部依赖，且不同发行版行为可能不同。

### 方案 B：容器（Podman/Docker）

**优点**：跨平台成熟、资源限制完善。
**缺点**：要求用户装容器运行时，与"Local-first 轻量本地服务"的定位冲突；
启动慢；在 MVP 阶段引入容器运行时属于过度依赖（§3.2「不为架构先进提前引入」）。
**否决**。

### 方案 C：仅 RLIMIT + 独立进程，不做沙箱

**优点**：无新依赖。
**缺点**：进程仍能读用户主目录、访问网络、读数据库文件——**不满足 §8.5**。
**否决**。

### 方案 D：WASM（Wasmtime）

§3.2 列为"后续候选"，M8 第 8 项才是"评估"。WASM 沙箱更严格，
但生态与工具链要求插件开发者会写 WASM，与"用户用自然语言造插件"的方向冲突。
**本期不采用，作为第 8 项的评估对象。**

### 推荐

**方案 A**，并加一道保险：**bwrap 不可用时自动降级为"拒绝运行进程插件"**
（而不是"无沙箱照常运行"）。这一条至关重要——沙箱缺失时降级为放行，
等于沙箱只是个摆设。

## 4. 信任模型

| 风险 | 处理 |
|---|---|
| 插件读取用户文件 | 沙箱内只挂载插件自己的目录（只读）与 `/usr`，看不到主目录与数据库 |
| 插件窃取密钥 | 环境变量白名单（PATH/LANG/TMPDIR），不继承宿主环境 |
| 插件外联 | `--unshare-net`，无网络；需要联网的能力本期不支持 |
| 插件耗尽资源 | RLIMIT_AS / RLIMIT_NPROC / RLIMIT_CPU + 墙钟超时 |
| 插件逃逸 | `--unshare-all`（user/pid/ipc/uts/cgroup）+ `--die-with-parent` + 无 `--cap-add` |
| 插件伪装权限 | 清单里的 permissions **只是声明**，实际由 Policy 决定（与 MCP 一致） |
| 恶意清单 | 严格 JSON 校验、未知字段拒绝、路径逃逸检查、大小上限 |
| 插件改写自身包 | 插件目录挂载为**只读** |
| 插件通过参数注入宿主 | 工具调用仍经 Broker 的 Schema 校验；参数以结构化 JSON 传递，不经 shell |

**风险级别**：进程插件的工具一律 `WRITE`（需审批）。这与 MCP 的决定一致，
理由也一样——即使是"读"，也可能把数据带出（虽然本期无网络，但插件可写
自己的文件，未来可能被读取）。

## 5. 具体设计

### 5.1 插件包结构

```
<数据目录>/plugins/<plugin-id>/
  plugin.json          # 清单（必需）
  <entrypoint>         # 可执行入口（仅进程插件需要）
```

清单（`plugin.json`）：

```json
{
  "id": "com.example.notes",
  "name": "笔记助手",
  "version": "1.0.0",
  "type": "declarative",          // declarative | process
  "description": "把笔记整理成待办",
  "runtime": "builtin",            // declarative 固定 builtin；process 用 sandbox
  "permissions": ["task:write"],
  "dependencies": [],
  "compatibility": ">=0.2.0",
  "source": "local",
  "tools": [
    {
      "name": "make_todo",
      "description": "把一段文本拆成待办",
      "display_name": "生成待办",
      "input_schema": {"type": "object", "properties": {"text": {"type": "string"}}, "required": ["text"]},
      "composes": ["builtin.create_task"]      // 声明式：复用已有工具
    }
  ],
  // 仅 process 类型
  "entrypoint": "run.sh",
  "limits": { "memory_mb": 256, "cpu_seconds": 10, "timeout_seconds": 30 }
}
```

### 5.2 两种插件类型

**declarative（声明式，本期默认）**

插件不包含可执行代码，只是**把已有能力组合成一个新工具**，
并声明它需要哪些权限。调用时 Broker 按 `composes` 顺序执行内建工具。

- 能做的事严格受限：只能调用用户已授权且已存在的能力；
- 风险极低：没有任何第三方代码被执行；
- 可以完整满足 M8 验收的"发现、授权、调用、停止、卸载"。

**process（进程插件，默认禁用）**

在沙箱内运行用户提供的可执行文件，通过 **JSON-RPC over stdio** 与宿主通信：

```
宿主要求 → {"jsonrpc":"2.0","method":"tools/call","params":{...}}
插件应答 → {"jsonrpc":"2.0","result":{"content":[{"type":"text","text":"..."}]}}
```

- **必须**在安装时勾选"我了解这将执行可执行文件"；
- bwrap 不可用 → 该插件标记为 `unavailable`，**不运行**；
- 每次调用启动一个沙箱进程，调用结束即退出（与 MCP 相同的确定性策略）。

### 5.3 与既有链路的关系

```
插件工具 → ToolBroker（参数校验 → Policy → 审批 → 执行 → 审计）
                ↓
     declarative: 依次调用已注册的内建工具（递归经过 Broker）
     process:     在 bwrap 沙箱中启动进程，JSON-RPC 通信
```

**仍然是同一条链路，没有第二套授权逻辑。**
进程插件的输出同样截断、同样标注不可信来源。

### 5.4 生命周期

| 操作 | 语义 |
|---|---|
| 安装 | 校验清单 → 显示来源/权限/依赖/风险 → 用户确认 → 复制到 `plugins/` |
| 启用 | 写入配置 `enabled: true`；进程插件还需确认"将执行代码" |
| 禁用 | 从注册表移除工具；进行中的调用允许结束 |
| 调用 | 每次调用一个新沙箱进程（declarative 则为同步组合） |
| 停止 | 杀掉运行中的沙箱进程（`--die-with-parent` 保证孤儿被回收） |
| 卸载 | 停止 → 移除注册 → 保留用户数据？**删除插件目录**（需二次确认） |

### 5.5 安装来源（本期）

- 本地目录（用户自己写的）；
- 本地 `.zip`（解压后校验，拒绝路径逃逸如 `../`、绝对路径、符号链接）；
- **暂不提供**从网络下载安装（那需要签名与来源校验，属 M10）。

## 6. 影响

| 维度 | 影响 |
|---|---|
| 数据 | 新增 `plugins/` 目录与 `plugins.json`（启用状态）。**无数据库迁移** |
| API | 新增 `GET /api/v1/plugins`（列表与状态）。安装/启用/卸载通过独立接口，均需确认 |
| 安全 | 新增"执行第三方代码"能力。默认禁用、沙箱缺失则拒绝运行、无网络、只读根 |
| 依赖 | **无新增 Python 依赖**；依赖系统已有的 `bubblewrap` 与 `prlimit`（util-linux） |
| 部署 | Linux 可用完整功能；其他平台降级为"仅 declarative 插件" |
| 维护 | 沙箱命令参数需要随 bwrap 版本关注；已用集成测试固定行为 |

## 7. 需要你决定的问题

1. **是否接受 bubblewrap 作为沙箱**（本机已实测可用、无新依赖）？
   - 接受 → 进程插件可行，功能完整。
   - 不接受 → 本期只做 declarative 插件，进程插件推迟到找到替代方案。
2. **是否本期就做进程插件**（执行第三方可执行文件），还是先只做 declarative？
   - `AGENT.md` M8 验收要求"隔离插件可以被发现、授权、调用、停止和卸载"。
     declarative 插件能满足全部动词，但严格说"隔离"的意义有限。
   - 我建议：**先做 declarative 完整闭环，再做进程插件**，分两次交付。
3. **卸载时是否删除插件目录**？
   - 删除（干净）vs 保留（可重装、防误删）。
   - 我建议**保留目录**、只取消注册，并提示用户手动删除——插件的配置
     可能包含用户自己的设置，自动删除不可逆。

## 8. 迁移与回滚

- **迁移**：无数据库迁移。现有用户不受影响（`plugins/` 不存在 = 没有插件）。
- **回滚**：删除 `app/plugins/`、`tests/test_plugins.py`，移除路由与接线。
  已安装插件留在数据目录，用户可手动删除。

## 9. 测试与验收

**单元**（不启动沙箱）

- 清单校验：未知字段、非法 id、版本、类型、路径逃逸、大小上限、工具名冲突
- declarative 组合：按 `composes` 递归调用，权限不足时拒绝
- 沙箱不可用 → 进程插件标记 unavailable 且**不被执行**
- 停止：卡住的进程被杀死，无孤儿残留

**集成**（真实 bwrap）

- 一个"试图读 `~/.ssh`"的测试插件 → 读不到
- 一个"试图连接外网"的测试插件 → 失败
- 一个"无限循环"的测试插件 → 被 RLIMIT_CPU / 超时杀死
- 一个"申请 2GB 内存"的测试插件 → 被 RLIMIT_AS 拒绝

**验收标准**

- [ ] 插件可被发现（能力页显示）
- [ ] 调用必须经 Broker 与 Policy，需审批
- [ ] 插件不能访问数据库文件与宿主密钥
- [ ] 插件不能访问网络（进程插件）
- [ ] 超时/超限的插件被终止，不影响宿主
- [ ] 停止与卸载语义明确、可追溯
- [ ] 后端全量测试通过

## 10. 实施顺序（批准后）

1. `app/plugins/manifest.py`：清单定义与严格校验（无执行逻辑）
2. `app/plugins/registry.py`：安装、启用、禁用、卸载、状态
3. `app/plugins/declarative.py`：声明式组合 → ToolDefinition
4. `app/plugins/sandbox.py`：bwrap 探测与沙箱命令构造 + 集成测试
5. `app/plugins/process.py`：JSON-RPC 进程插件
6. API + 前端「插件」页
7. 文档（D-017）

第 1–3 步不涉及执行第三方代码，风险最低，可先交付验收。
第 4–5 步涉及沙箱，单独提交并用集成测试证明隔离有效。
