## 1. 评估方法

不凭印象判断，在**本机实际运行**了以下实验（`wasmtime` Python 绑定，独立虚拟环境）：

| 实验 | 目的 |
|---|---|
| 无限循环 + fuel 预算 | CPU 限制的精度 |
| 未预授权目录下的 `path_open` | 文件系统隔离强度 |
| `memory.grow` 与超大初始内存 | 内存限制的时机与强度 |
| 冷启动计时（WASM vs bwrap） | 性能对比 |
| 同一功能的两种写法 | 插件作者的开发成本 |

---

## 2. 实测结果

### 2.1 隔离强度：WASM 更强

| 维度 | bubblewrap（当前方案） | Wasmtime（评估） |
|---|---|---|
| 文件系统 | 未挂载 → 可见但**不可读**；存在性可探测 | 未预授权 → `path_open` 直接返回 `EACCES`，**连存在性都探测不到** |
| 网络 | 无网络命名空间 | WASI 默认无 socket；未授权即不可能 |
| 系统调用 | 进程可发起任意 syscall，靠命名空间+seccomp 限制 | **默认零系统调用**，只能调用宿主显式导入的函数 |
| 内存 | `RLIMIT_AS`，运行时触发 `MemoryError` | 模块声明上限，**加载时**即拒绝超限模块 |
| CPU | `RLIMIT_CPU`，**秒级粒度** | `consume_fuel`，**指令级**；实测 1ms 内终止无限循环 |

WASM 是**能力模型**（默认什么都没给），bwrap 是**权限收窄**（先给全部再剥掉）。
前者的攻击面在原理上更小。

### 2.2 性能：WASM 更快

| 指标 | bubblewrap | Wasmtime |
|---|---|---|
| 冷启动 | ≈ 7 ms（进程 + 命名空间） | ≈ 0.5–0.6 ms（引擎+编译+实例化+调用） |
| 单次编译 | — | ≈ 2 ms（可缓存复用） |
| 常驻开销 | 每个调用一个进程 | 可在同一进程内运行 |

### 2.3 开发成本：WASM 高得多

这是**决定性因素**。

当前（bwrap）插件作者写一个 Python 文件即可：

```python
import json, sys
p = json.loads(sys.stdin.read() or "{}")
print(json.dumps({"ok": True, "content": f"回声：{p['arguments']['text']}"}))
```

WASM 需要：先装 Rust/C/Go 工具链 → 写代码 → 编译成 `wasm32-wasi`
→ 打包。同一功能在 WAT 里要手工构造 iovec 调 `fd_write`；
而且 WASI 没有内置 JSON 解析，参数传递格式需要另定。
**本机目前未安装任何 WASM 编译工具链。**

对"用户是学习者、希望通过自然语言创建能力"的项目定位（§1.5、§1.3 的
Natural-language Creation）来说，这是一个显著的反向因素。

### 2.4 生态与维护

- `wasmtime` PyPI 包：MIT/Apache-2.0 双许可，官方维护，无额外运行时依赖（Rust 编译的轮子）。
- WASI 标准仍在演进（preview2 尚未全面落地），API 可能变化。
- 引入它需要新增依赖；若只作为"可选更强隔离层"，则需要两套插件运行时并存。

## 3. 备选方案

### 方案 A：全面切换到 WASM，替换 bubblewrap

- **优点**：隔离最强、最快、可同进程运行。
- **缺点**：现有进程插件全部需要重写并重新编译；作者门槛陡增（需 Rust/Go 工具链）；
  WASI 标准仍在演进。**否决**——与"降低用户创造能力的门槛"直接冲突。

### 方案 B：双运行时并存（bwrap 默认，WASM 可选）

- **优点**：高安全需求的插件可以选 WASM。
- **缺点**：两套沙箱、两套协议、两份文档与测试矩阵；当前**没有任何真实需求**
  要求超出 bwrap 的隔离强度。**暂不采用**（违反 §0.4「不为架构先进提前引入」）。

### 方案 C：不引入，记录为待评估（推荐）

- 当前 bwrap 的隔离已满足 §8.5 的全部硬性要求，且经真实攻击测试验证
  （见 D-018：主目录不可读、数据库不可见、网络阻断、CPU/内存受限、密钥不泄漏）。
- 当出现以下**触发条件**之一时重新评估：
  1. 需要运行**不可信来源**的插件（社区插件、M10 生态）；
  2. 需要更细的资源计量（按插件的 fuel/内存配额做计费或限流）；
  3. 跨平台需求（macOS/Windows 无 bwrap，而 WASM 天然跨平台）；
  4. WASI preview2 稳定，且出现了成熟的 Python→WASM 工具链
     （那会抹平第 2.3 节的开发成本差距）。

**选择方案 C。**

---

## 4. 结论

| 维度 | 判断 |
|---|---|
| 隔离强度 | WASM 明显更强（能力模型 vs 权限收窄） |
| 性能 | WASM 更快（<1ms vs ~7ms） |
| 开发成本 | bubblewrap 明显更低（一个 Python 文件 vs 工具链+编译） |
| 当前需求匹配度 | bubblewrap 已满足 §8.5 全部要求 |
| **决定** | **暂不引入 WASM；记录触发条件，届时重新评估** |

**核心判断**：WASM 的优势（更强隔离、更快）在本项目中**目前不是瓶颈**，
而它的成本（插件作者需要 Rust/Go 工具链）会直接削弱产品的核心价值主张。
等真正需要运行不可信来源插件（M10 社区生态）时，收益才会超过成本。
